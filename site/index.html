Method and caveats

Self-hosted station pulls
GitHub has no API for container download counts, so the collector scrapes each image's package "versions" page daily and resolves every digest through the registry (index / per-platform index / platform manifest / attestation). Digests sharing platform manifests are one build. A build is main if its index carried the main tag in a daily snapshot, otherwise it takes the branch of the nearest successful CI run; its release is the newest tag committed before it was built. Images carry no labels, so before tag evidence starts (2026-08-25), builds whose main and staging runs started within two minutes of each other can't be told apart and count as main (mixed, marked *).
Automated pulls
Since , a station update via install.sh pulls each image once, so backend and frontend platform pulls move 1:1. docker compose pull — by hand, from a script or a per-container updater — pulls the backend once per service using it, :1. Each day, per architecture, (backend − frontend) ÷ frontend pulls count as automated; they come off the builds pulled most that day, because a compose pull follows one tag. Pulls before the first snapshot are split the same way once. Automated pulls are not station updates and are left out of every estimate.
Self-hosted estimate
One cohort model per update channel (Release = main, Latest = staging), stepping build by build, since untagged pushes to main are offered as updates too. Each build's station pulls (minus maintainer station on main) drain proportionally from the pool of stations on older builds; the excess is new stations. The pool equals the largest single wave of pulls, so the estimate is a floor: stations that skipped that build are missed. The high end assumes only of active stations take any given build, capped by the pulls actually seen. Stations whose build was replaced more than days ago count as "not updating". Stations that build locally (32-bit ARM, a UID other than 1000, an update before CI finished) never pull and are invisible.
Home Assistant estimate
Each install pulls an add-on version once when it updates. Of the two newest versions out at least 7 days, the more-pulled one is the estimate and the other the low end, neither below HA analytics' opt-in count. The high end scales the estimate by the share of opt-in installs on one of those versions or newer, since the rest never pulled them. Opt-in rate is reporting ÷ estimate.
Total
Self-hosted + Home Assistant; the range adds the low ends and the high ends.
